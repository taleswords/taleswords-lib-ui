# lib-ui 2.4.3 Technical Proposal

## DropdownBase Panel Width Behavior Stabilization

### Status

Implemented (v2.4.3)

### Target Release

lib-ui **v2.4.3**

### Affected Component

`DropdownBase`

```
src/components/DropdownBase/Base.vue
```

---

# 1. Summary

This proposal recommends modifying the panel width calculation logic in `DropdownBase` to use **`min-width` instead of a fixed `width`** derived from the trigger element.

The change improves flexibility for dropdowns triggered by compact controls (e.g., icon buttons) while preserving backward compatibility with existing layouts.

---

# 2. Current Behavior

`DropdownBase` currently forces the dropdown panel width to match the trigger width.

Implementation:

```javascript
menuContainerRef.value.style.width = `${triggerRect.width}px`
```

As a result:

```
panel width = trigger width
```

This behavior works well when the trigger is a standard button or input field.

However, it introduces significant usability issues when the trigger element is intentionally compact, such as:

* icon buttons
* toolbar controls
* action icons
* command palette triggers

In these cases the panel becomes extremely narrow and may produce horizontal overflow.

Example scenario:

```
Trigger width: 32px
Dropdown panel width: 32px
Search results: truncated
Horizontal scrolling required
```

---

# 3. Problem Statement

The current width enforcement assumes that the trigger width represents the appropriate layout width for the dropdown content.

This assumption fails for modern UI patterns where:

* the trigger is a **minimal affordance**
* the dropdown is **content-heavy**

Common examples:

| Pattern          | Trigger     | Panel Content            |
| ---------------- | ----------- | ------------------------ |
| Toolbar search   | icon button | searchable results list  |
| Command palette  | icon        | command list             |
| Node search      | icon        | graph navigation results |
| Context selector | icon        | large option set         |

Because the width is enforced via **inline style**, consumer CSS cannot override it without using fragile global rules.

This creates unnecessary limitations for consumers of the component.

---

# 4. Proposed Change

Replace the forced `width` assignment with `minWidth`.

### Current implementation

```javascript
menuContainerRef.value.style.width = `${triggerRect.width}px`
```

### Proposed implementation

```javascript
menuContainerRef.value.style.minWidth = `${triggerRect.width}px`
```

---

# 5. Resulting Behavior

After the change:

| Scenario          | Result                         |
| ----------------- | ------------------------------ |
| Standard dropdown | panel ≥ trigger width          |
| Large trigger     | panel matches trigger          |
| Small trigger     | panel expands to content width |
| Consumer override | possible via CSS               |

Example consumer usage:

```css
.node-search-dropdown {
  min-width: 280px;
}
```

Result:

```
Trigger: 32px icon
Panel: 280px
Content readable
No horizontal scroll
```

---

# 6. Compatibility

This change is **backward compatible**.

Existing layouts relying on equal trigger/panel width remain unaffected because:

```
panel min-width = trigger width
```

In typical dropdown scenarios the panel width is already constrained by content or container layout.

No existing API or prop contracts change.

---

# 7. Benefits

### 7.1 Increased Flexibility

Consumers can define panel width through CSS when required.

### 7.2 Modern UI Pattern Support

Supports patterns where the trigger is smaller than the content surface.

Examples:

* search dropdowns
* command palettes
* node navigation
* contextual inspectors

### 7.3 Eliminates Consumer Workarounds

Without this change consumers must rely on:

* global CSS overrides
* teleport targeting
* layout hacks
* trigger wrapper width inflation

These approaches are brittle and violate encapsulation.

### 7.4 Aligns With Web UI Conventions

Many UI frameworks follow the pattern:

```
dropdown min-width = trigger width
```

Examples:

* Radix UI
* Headless UI
* MUI menus
* Chakra menus

Scope:

Affected file:

# 9. Testing Requirements

### Icon Trigger

### Consumer CSS Override

```css

  min-width: 260px;
}
```

Ensure the panel respects the override.

### Keyboard Navigation

Confirm no regression in:

* arrow navigation
* search filtering
* option selection
* panel positioning

---

# 10. Risks

Risk level: **Low**

The change does not alter:

* positioning logic
* focus management
* keyboard navigation
* option rendering
* teleport behavior

Only the width constraint mechanism changes.

---

# 11. Conclusion

Replacing the forced panel width with a `min-width` constraint significantly improves the flexibility and usability of `DropdownBase` without introducing breaking changes.

The modification enables support for modern UI patterns while preserving existing behavior for traditional dropdown triggers.

This adjustment is small, safe, and appropriate for inclusion in **lib-ui v2.4.3**.
