# @taleswords/lib-ui

# Enhancement Proposal — 2.1.0

**Title:** Inspector & Foundation Expansion
**Status:** Implemented
**Target Version:** 2.1.0 (Minor)
**Date:** 2026-03

---

# 1. Executive Summary

This proposal introduces three additive, non-breaking enhancements to the Foundation layer of `@taleswords/lib-ui`:

1. Multiline support for `TextboxBase`
2. New `DisplayFieldBase` component (pure display primitive)
3. `defaultExpanded` support for `AccordionBase`

These changes are:

* 100% backward compatible
* Fully doctrine-compliant
* Token-architecture aligned
* Foundation-layer safe
* Domain-agnostic
* Systemically beneficial beyond the Inspector use case

Version bump: **Minor (2.1.0)**
Rationale: introduction of new component + meaningful primitive capability expansion.

---

# 2. Motivation

## 2.1 Systemic Gaps Identified

During the redesign of the Editor Inspector panel, the following systemic gaps were identified in lib-ui:

| Gap                                             | Severity | Systemic? |
| ----------------------------------------------- | -------- | --------- |
| No multiline text input primitive               | High     | Yes       |
| No pure display field component (key/value)     | High     | Yes       |
| No contextual default-open control in Accordion | Medium   | Yes       |

The Inspector is merely the catalyst. These gaps affect any data-heavy panel or admin UI built on lib-ui.

# 3. Enhancement 1 — Multiline Support in TextboxBase

## 3.1 Problem

`TextboxBase` currently renders `<input>` only.
There is no supported multiline text primitive.

Consumers must:

* Use raw `<textarea>`
* Or style locally (violates UI Purity Rule)

---

## 3.2 Proposed API

Add optional props:

```
multiline?: boolean
rows?: number
autosize?: boolean
```

Behavior:

* `multiline === false` (default) → current `<input>`
* `multiline === true` → render `<textarea>`
* `rows` respected only when multiline
* `autosize` optionally adjusts height dynamically

All existing props remain unchanged.

---

## 3.3 Doctrine Compliance

* Foundation layer only
* No store imports
* Base.vue naming preserved
* Token usage only (no hardcoded hex)
* Dark theme supported
* No existing behavior modified

---

## 3.4 Risk Assessment

Risk: **Very Low**

* Additive prop only
* Default behavior unchanged
* No prop renames
* No token renames
* No style mutation

---

# 4. Enhancement 2 — DisplayFieldBase (New Component)

## 4.1 Problem

lib-ui lacks a pure display primitive for key/value data.

Consumers currently:

* Use `FormField` for display (incorrect interactive semantics)
* Use custom div wrappers (violates purity rule)

---

## 4.2 Proposed Component

### Name

`DisplayFieldBase.vue`

### Layer

Foundation

### Purpose

Domain-agnostic key/value display primitive.

---

## 4.3 Proposed API

```
props:
  label: string
  value?: string | number | null
  inline?: boolean
  isMuted?: boolean
  truncate?: boolean

slots:
  default (optional override for value)
```

---

## 4.4 Behavior

Default vertical layout:

Label
Value

Optional inline layout:

Label: Value

No focus styling. No pointer cursor. No interactive affordances.

---

## 4.5 Token Strategy

New tokens:

```
--display-field-label-color
--display-field-value-color
--display-field-label-font
--display-field-value-font
```

Must:

* Reference semantic layer
* Respect dark theme override
* Follow naming doctrine conventions

No new palette colors introduced.

---

## 4.6 Risk Assessment

Risk: **Low**

* New export only
* No mutation of existing components
* No breaking token changes

---

# 5. Enhancement 3 — Accordion defaultExpanded Support

## 5.1 Problem

`AccordionBase` initializes with empty expanded state.

Consumers must manually call `expandAll()` via template refs.

This creates lifecycle coupling and orchestration complexity.

---

## 5.2 Proposed API

```
defaultExpanded?: string[] | 'all'
```

Behavior:

* On mount, initialize expanded state accordingly
* No change to runtime toggle behavior
* Does not create controlled accordion

Optional future enhancement: emit `@expand(id)` and `@collapse(id)` events.

---

## 5.3 Risk Assessment

Risk: **Very Low**

Pure initialization enhancement. Backward compatible.
