# Enhancement Proposal — 2.4.0

**Title:** AccordionItem Trigger Slots & FormField Label Suffix Slot
**Status:** Accepted — Implemented in 2.4.0
**Target Version:** 2.4.0 (Minor)
**Date:** 2026-03

---

# 1. Executive Summary

This proposal adds optional named slots to two existing components:

**AccordionItem** — `trigger-prefix` and `trigger-suffix` slots, allowing consumers to render auxiliary content (badges, counts, icons) inside the accordion trigger button alongside the title text.

**FormField** — `label-suffix` slot, allowing consumers to render inline indicators (saving spinners, status icons, character counts) adjacent to the field label.

Both enhancements share the same architectural pattern: optional named slots with conditional wrapper elements that emit zero DOM when unused.

This is an additive API enhancement only.

No existing props removed.
No existing behavior changed.
No token renaming.
No breaking API changes.

---

# 2. Background

Two component limitations were identified during the Power Inspector audit for taleswords-web (2026-03).

## 2.1 AccordionItem

AccordionItem currently accepts a `title` string prop and renders it as the sole content of the trigger button. The trigger layout is:

```
[ title text .......................... chevron icon ]
```

There is no mechanism to place additional content (badges, counters, status indicators, icons) inside the trigger row.

The inspector requires severity badges and signal counts inside accordion section headers to communicate governance state at a glance, without requiring the user to expand each section.

## 2.2 FormField

FormField currently renders its label as a `<label>` element with `display: block`, containing only the label text and a required/optional indicator. The label layout is:

```
Label Text *
```

There is no mechanism to place inline indicators (saving spinners, status icons, validation feedback) adjacent to the label. The only slot is `default`, which renders the form control below the label row.

The inspector requires field-level saving indicators and status feedback visible at the label level, without rebuilding the label outside of FormField.

---

# 3. Problem Statement

## 3.1 AccordionItem

Without trigger slots, consumers who need auxiliary content in accordion headers must choose between:

1. **External composition** — placing badges outside the accordion item, breaking the visual association between the indicator and the section it describes.
2. **CSS overrides** — targeting `.accordion-item__trigger` from the consumer, violating the sealed component contract defined in CLAUDE.md (§4, §7).
3. **Forking the component** — duplicating AccordionItem logic in the consumer, creating maintenance burden and divergence.

## 3.2 FormField

Without a label-suffix slot, consumers who need inline indicators next to the field label must choose between:

1. **External wrapper** — placing the indicator outside FormField and adding app-level CSS to visually align it with the label, bypassing FormField's internal layout.
2. **Omitting FormField's label** — passing no `label` prop and rebuilding the entire label row (text, required star, optional indicator, focus-within color transition) manually in the default slot, duplicating FormField's internal logic.
3. **CSS overrides** — targeting `.form-field__label` from the consumer, violating the sealed component contract.

None of these options are acceptable for a governed design system.

---

# 4. Proposal

## 4.1 AccordionItem

Add two optional named slots to AccordionItem:

* `trigger-prefix` — rendered before the title text
* `trigger-suffix` — rendered after the title text, before the chevron icon

Both slots are purely additive. When unused, the component renders identically to 2.3.0.

## 4.2 FormField

Add one optional named slot to FormField:

* `label-suffix` — rendered inline after the label text and required/optional indicator, before the description

The slot is purely additive. When unused, the component renders identically to 2.3.0.

# 5. API Design — AccordionItem

## 5.1 Current AccordionItem API (2.3.0)

```typescript
interface AccordionItemProps {
    id: string
    title: string
    isDisabled?: boolean
}

// Slots:
//   default — panel content
```

## 5.2 Proposed AccordionItem API (2.4.0)

```typescript
// Props unchanged
interface AccordionItemProps {
    id: string
    title: string
    isDisabled?: boolean
}

// Slots:
//   default          — panel content (unchanged)
//   trigger-prefix   — content before title text (new)
//   trigger-suffix   — content after title text, before chevron (new)
```

No new props. No changed props. No changed emits.

## 5.3 Slot Typing

```typescript
defineSlots<{
    default?: () => unknown
    'trigger-prefix'?: () => unknown
    'trigger-suffix'?: () => unknown
}>()
```

## 5.4 Template Change

Current trigger structure:

```html
<button class="accordion-item__trigger" ...>
    <span class="accordion-item__title">{{ title }}</span>
    <span class="accordion-item__icon" ...>expand_more</span>
</button>
```

Proposed trigger structure:

```html
<button class="accordion-item__trigger" ...>
    <span
        v-if="$slots['trigger-prefix']"
        class="accordion-item__trigger-prefix"
    >
        <slot name="trigger-prefix" />
    </span>
    <span class="accordion-item__title">{{ title }}</span>
    <span
        v-if="$slots['trigger-suffix']"
        class="accordion-item__trigger-suffix"
    >
        <slot name="trigger-suffix" />
    </span>
    <span class="accordion-item__icon" ...>expand_more</span>
</button>
```

The wrapper `<span>` elements are only rendered when the slot is provided, ensuring zero DOM overhead when slots are unused.

## 5.5 Styling

New BEM classes, fully token-driven:

```css
.accordion-item__trigger-prefix,
.accordion-item__trigger-suffix {
    display: flex;
    align-items: center;
    flex-shrink: 0;
}

.accordion-item__trigger-prefix {
    margin-right: calc(0.5em * var(--density-scale));
}

.accordion-item__trigger-suffix {
    margin-left: auto;
    margin-right: calc(0.5em * var(--density-scale));
}
```

The suffix uses `margin-left: auto` to push itself and the chevron to the right, while the title occupies remaining space. This preserves the existing `justify-content: space-between` layout when no suffix is present, and creates a natural `[ title ... suffix chevron ]` arrangement when it is.

All spacing uses `--density-scale` to remain density-aware.

No new tokens introduced. Existing `--accordion-*` tokens govern font, color, and background. The slot containers inherit from the trigger and add only density-scaled margins.

# 6. API Design — FormField

## 6.1 Current FormField API (2.3.0)

```typescript
interface FormFieldProps {
    label?: string
    description?: string
    isOptional?: boolean
    display?: boolean
    validationData?: ValidationEntry | ValidationEntry[] | Record<string, unknown>
}

// Slots:
//   default — form control
```

## 6.2 Proposed FormField API (2.4.0)

```typescript
// Props unchanged
interface FormFieldProps {
    label?: string
    description?: string
    isOptional?: boolean
    display?: boolean
    validationData?: ValidationEntry | ValidationEntry[] | Record<string, unknown>
}

// Slots:
//   default        — form control (unchanged)
//   label-suffix   — inline content after label text and required/optional indicator (new)
```

No new props. No changed props. No changed emits.

## 6.3 Slot Typing

```typescript
defineSlots<{
    default?: () => unknown
    'label-suffix'?: () => unknown
}>()
```

## 6.4 Template Change

Current label structure:

```html
<label v-if="props.label" class="form-field__label">
    {{ props.label }}
    <span v-if="!props.isOptional" class="form-field__required" aria-label="required">*</span>
    <span v-else class="form-field__optional">(optional)</span>
</label>
```

Proposed label structure:

```html
<div v-if="props.label || $slots['label-suffix']" class="form-field__label-row">
    <label v-if="props.label" class="form-field__label">
        {{ props.label }}
        <span v-if="!props.isOptional" class="form-field__required" aria-label="required">*</span>
        <span v-else class="form-field__optional">(optional)</span>
    </label>
    <span
        v-if="$slots['label-suffix']"
        class="form-field__label-suffix"
    >
        <slot name="label-suffix" />
    </span>
</div>
```

Key design decisions:

* The `<label>` element is preserved exactly as-is. The slot content renders in a sibling `<span>`, not inside the `<label>`, so it does not affect the label's accessible name or the label-to-input association.
* A `<div class="form-field__label-row">` wrapper is introduced to create a flex row. This wrapper renders only when `label` is provided or the `label-suffix` slot is used.
* When `label-suffix` is unused and `label` is provided, the label-row wrapper still renders but contains only the `<label>`. The visual output is identical because the flex row with a single block-level child produces the same layout as the current bare `<label>`.

## 6.5 Styling

New BEM classes, fully token-driven:

```css
.form-field__label-row {
    display: flex;
    align-items: baseline;
    gap: calc(0.5em * var(--density-scale));
}

.form-field__label-suffix {
    display: flex;
    align-items: center;
    flex-shrink: 0;
    margin-left: auto;
}
```

The label-row uses `align-items: baseline` so the label text and suffix content share a common text baseline. The suffix uses `margin-left: auto` to push itself to the right edge of the label row.

All spacing uses `--density-scale` to remain density-aware.

No new tokens introduced. The suffix container inherits the label row's font context.

## 6.6 Focus-Within Behavior

The existing focus-within rule:

```css
.form-field:not(.form-field--display):focus-within .form-field__label {
    color: var(--form-field-label-focus-color);
}
```

This continues to work unchanged. The rule targets `.form-field__label` specifically, which remains the `<label>` element. The label-suffix span is not affected by this rule, which is correct — the suffix content (spinners, icons) should not change color on focus.

# 11. Accessibility

## 11.1 AccordionItem — Slot Content Inside Button

Both trigger slots render inside the `<button>` element. Content placed in these slots becomes part of the button's accessible name computation.

Consumers must ensure slot content does not introduce interactive elements inside the button (no nested buttons, links, or inputs). This is a standard HTML constraint, not specific to this proposal.

Decorative slot content (icons, badges) should use `aria-hidden="true"` when the information is redundant with the title or conveyed elsewhere.

## 11.2 AccordionItem — Screen Reader Behavior

BadgeBase renders as a `<span>` with text content. When placed in the trigger-suffix slot, its text is included in the button's accessible name:

```
Accessible name: "Pepper Signals 3 expand_more"
```

To provide cleaner announcements, consumers can add `aria-label` to the badge wrapper:

```vue
<template #trigger-suffix>
    <span aria-label="3 errors">
        <BadgeBase variant="danger" label="3" size="sm" />
    </span>
</template>
```

## 11.3 AccordionItem — Focus Ring

No changes to focus ring behavior. The existing `outline` on `.accordion-item__trigger:focus-visible` covers the full button area including slot content.

## 11.4 AccordionItem — Keyboard Navigation

No changes. The trigger remains a single `<button>`. Enter/Space toggles.

## 11.5 FormField — Label-Suffix Isolation

The `label-suffix` slot renders in a sibling `<span>` outside the `<label>` element. This is a deliberate design decision:

* The `<label>` accessible name is unaffected by suffix content.
* The label-to-input click association (clicking label focuses the input) is preserved without interference from suffix content.
* Suffix content (spinners, badges) is announced separately by screen readers as inline content, not as part of the label.

If the suffix conveys important status information, consumers should ensure it has appropriate ARIA attributes:

```vue
<template #label-suffix>
    <LoaderIcon v-if="isSaving" size="small" aria-label="Saving" role="status" />
</template>
```

Note: `LoaderIcon` has `aria-hidden="true"` by default. Consumers placing it in label-suffix should override this with an explicit `role="status"` and `aria-label` when the saving state is meaningful.

## 11.6 FormField — Focus-Within

The existing focus-within color transition targets `.form-field__label` specifically. The label-suffix span is not affected. This is correct — suffix indicators should not change color when the input receives focus.

# 13. Migration Notes

## From 2.3.0 to 2.4.0

No migration required for either component.

* No props removed or renamed
* No behavioral changes to existing API
* No token changes
* No CSS class renaming
* `AccordionItemProps` type unchanged
* `FormFieldProps` type unchanged

Consumers using either component without the new slots will see zero differences.

**FormField DOM note:** The label element is now wrapped in a `.form-field__label-row` div. This wrapper renders even when `label-suffix` is unused (when `label` is provided). The visual output is identical because a flex row with a single block-level child produces the same layout. However, consumers with CSS selectors targeting `.form-field > .form-field__label` (direct child) will need to update to `.form-field__label-row > .form-field__label`. This is unlikely because CLAUDE.md doctrine (§4) prohibits consumer overrides of component internals, but it is noted for completeness.

## Type Exports

Neither `AccordionItemProps` nor `FormFieldProps` interfaces change. No new type exports required. Slots are defined via `defineSlots` and do not affect props interfaces.

# 14. Non-Goals

This proposal does NOT:

* Add a `subtitle` or `description` prop to AccordionItem
* Add a full `trigger` override slot that replaces the entire button
* Modify AccordionBase parent API
* Change the expand/collapse animation
* Add per-item event hooks
* Introduce conditional slot rendering based on expanded state
* Add a full `label` override slot to FormField
* Add `label-prefix` to FormField (no identified use case)
* Add slots to the description or error regions of FormField

These are potential future enhancements, not part of 2.4.0.

# 16. Risks

Risk Level: Low

| Risk | Likelihood | Impact | Mitigation |
| ---- | ---------- | ------ | ---------- |
| Consumer places interactive element in AccordionItem trigger slot | Low | Accessibility violation (nested button) | Document constraint in playground; linting is consumer responsibility |
| Slot content causes accordion trigger height to vary across items | Low | Visual inconsistency | Slot wrappers use `align-items: center` and `flex-shrink: 0`; badges have fixed height |
| AccordionItem suffix content overflows on narrow containers | Low | Layout break | `flex-shrink: 0` on suffix; title has natural text wrapping; density scaling reduces spacing in compact mode |
| FormField label-row wrapper changes DOM structure | Low | CSS selector breakage in consumers | Doctrine prohibits consumer overrides of component internals; noted in migration notes |
| FormField label-suffix content is too tall | Low | Label row height increase | `align-items: baseline` keeps text aligned; `flex-shrink: 0` prevents collapse; `LoaderIcon small` is 16px — close to label line height |

No architectural risks. No token system impact. No floating positioning impact.

# 19. Conclusion

AccordionItem and FormField are well-tested, accessible, density-aware components. Both share the same structural limitation: no mechanism to place auxiliary content alongside their primary text element.

Three named slots resolve this cleanly:

* AccordionItem: `trigger-prefix` and `trigger-suffix`
* FormField: `label-suffix`

All three follow the same pattern:

* Zero breaking changes
* Zero DOM overhead when unused
* Full density and token compliance
* Clear accessibility contract

This enables taleswords-web to render severity badges, signal counts, saving indicators, and status feedback directly inside component headers and label rows — the primary requirements identified in the Power Inspector audit.

Proposal ready for review.
