### Why one release, and why a minor

Every change is additive: one new union member (B), new behaviour only where a row overflows (A), one new token with both controls adopting it (C), two new palette greys and re-pointed border tokens (D). No prop, event, slot or token is removed or renamed, and no consumer must change code. CLAUDE.md §10 names "token changes" under Major next to "breaking API"; this bundle changes token *values* (D) and adds tokens (C, D) without breaking any consumer contract, so it is filed as a minor, as 2.3.0 (the spacing and density tokens) was. If that reading of §10 is not accepted, the alternative is to ship D alone as 3.0.0; this proposal does not recommend it.

# RFC 2.7.0-A — TabsBase: an overflowing tab row scrolls and shows it

## Affected component

`src/wrappers/tabs/Base.vue`, `src/styles/tokens.css`, `src/styles/tokens-dark.css`

## 1. Summary

When the tabs are wider than the list, the list scrolls sideways and shows that there is more: a fade with a pressable chevron on each edge beyond which tabs lie. The selected tab is kept in view. The tab gains the focus style it lacks. A row that fits looks and behaves exactly as today.

## 2. Current behavior (main 4b60031)

- The list is `display: flex` with no overflow rule (`Base.vue:165-170`); each tab is `white-space: nowrap` (`Base.vue:183`). A row wider than its container runs past the edge. On /admin with five tabs at 375 CSS px the row is 374.6 px wide, 39.6 px wider than its column, and the last tab ("Log") is cut and cannot be reached by touch or pointer. This is a WCAG 1.4.10 Reflow failure at 320 CSS px (400% zoom at a desk).
- The tab button defines default, hover, active and disabled (`Base.vue:172-201`) but **no focus style**: the only `:focus-visible` rule is the panel's (`Base.vue:221-225`). CLAUDE.md §6 requires a visible focus ring on every interactive component; color doctrine §10 requires a focus state.
- The indicator is positioned from `offsetLeft`/`offsetWidth` on mount and on `modelValue` change only (`Base.vue:53-72`); it is not recomputed on resize.

## 3. Proposed behavior

1. **Scroll.** `.tabs-base__list` becomes a scroll container on the inline axis (`overflow-x: auto`, the scrollbar hidden: `scrollbar-width: none` and the WebKit equivalent). Touch, trackpad and shift+wheel scroll it. No wheel handler is added, so a vertical wheel over the row still scrolls the page.
2. **Shows there is more.** A wrapper `.tabs-base__list-wrap` (position: relative) holds the list and two edge controls, `.tabs-base__edge--start` and `.tabs-base__edge--end`. An edge is rendered only while tabs lie beyond it. Each edge is a 40 px wide fade from transparent to the ground with a 20 px chevron (`chevron_left` / `chevron_right`, Material Symbols, as the library's other icons); **the whole fade is the press target** (40 × the row's height), as the design's states sheet draws it. Pressing it scrolls the row by about 80% of its visible width, smoothly unless `prefers-reduced-motion` is set.
3. **The edges are not tab stops.** They are `<button type="button" tabindex="-1" aria-hidden="true">`: a pointer and touch convenience. Keyboard and assistive-technology users already reach every tab with Arrow, Home and End, and the row follows focus (4). This keeps the tablist's roving tabindex and its accessible tree exactly as today.
4. **The selected tab stays in view.** On mount and whenever `modelValue` changes, the active tab is scrolled into view (`scrollIntoView({ block: 'nearest', inline: 'nearest' })`, called on the tab, so only the list scrolls). Since Arrow/Home/End select the tab they focus, the focused tab is never off-screen.
5. **The indicator stays under its tab.** It is a child of the scrolling list and is positioned from `offsetLeft`, which is relative to the list's content, so it moves with the tabs while the row scrolls. It is additionally recomputed on resize (a `ResizeObserver` on the list, which also drives the edges' visibility together with the list's `scroll` event).
6. **Focus style on the tab.** `.tabs-base__tab:focus-visible` gets `outline: 2px solid var(--general-focus-ring)` with `outline-offset: -2px` and the library's `--radius-xs`: drawn **inside** the tab, so a scrolling container never clips it. Blue, as color doctrine §4 rules for the focus ring.

New semantic tokens (both themes): `--tabs-edge-fade` (the ground the fade ends in; `--general-body-bg` by default) and `--tabs-edge-icon-color` (the chevron; `--tabs-tab-color`).

## 4. Implementation strategy

- Template: wrap the list; add the two edge buttons with `v-if="hasStart"` / `v-if="hasEnd"`.
- Script: `hasStart = scrollLeft > 1`, `hasEnd = scrollLeft + clientWidth < scrollWidth - 1`, updated on `scroll` (passive), on the `ResizeObserver` callback and after `tabs` changes; `scrollBy` for the edges; `scrollIntoView` in the existing mount and `modelValue` watchers.
- No new prop, event or slot. No new dependency.

## 5. Hard stops

- **Accessibility guarantees:** restores Reflow (1.4.10) and adds the missing focus ring (2.4.7). Roles, `aria-selected`, `aria-controls`, roving `tabindex` and the Arrow/Home/End keys are untouched.
- **Token architecture:** two semantic tokens added in the existing `--tabs-*` family; they reference semantic tokens only.

## 6. Tests

- Unit (`src/__tests__/wrappers/TabsBase.test.ts`, 16 tests today): edges absent when the row fits; rendered per edge when it does not (scroll metrics stubbed, as jsdom has no layout); `scrollIntoView` called on mount and on `modelValue` change; edges are `aria-hidden` and not tab stops; vitest-axe still passes; the `:focus-visible` rule exists.
- Contract (`tests/contracts/tabs.spec.ts`, new, Playwright): a 320 px and a 375 px container with five tabs: every tab reached by Arrow/End and fully visible; the end edge visible at the start and gone at the end; pressing an edge scrolls; opening on the last tab shows it; the indicator's box sits under the selected tab after a scroll and after a resize; no edge when the row fits.
- Playground: the tabs page gains a narrow-container example in both themes.

## 7. Backward compatibility

A row that fits: no edge is rendered, no scroll, no layout shift. The one change every consumer sees is the tab's focus ring on keyboard focus. The new wrapper element sits inside the scoped root, so no consumer selector is affected.

## 8. Out of scope

A wrapping row; a "more" menu; making the edges keyboard-focusable; card #958's bug (the indicator under the wrong label when the tab is restored from the session preference) — if the resize observer closes it, that is said on #958, not claimed here.

# RFC 2.7.0-B — TextboxBase gains the `date` type

## Affected component

`src/inputs/textboxes/Base.vue`, `docs/public-api.md`

## 1. Summary

`TextboxType` gains `'date'`: TextboxBase renders the browser's own date input with its native picker. No date library and no calendar component.

## 2. Current behavior (main 4b60031)

`TextboxType` is `'text' | 'email' | 'password' | 'number' | 'search' | 'tel' | 'url'` (`Base.vue:6`), passed straight to `<input :type>` (`Base.vue:133`). There is no way to draw a date field with lib-ui; the UI doctrine forbids a raw `<input>` in application code.

## 3. Proposed behavior

- `TextboxType` gains `'date'`.
- The value stays a **string in the browser's ISO form** (`YYYY-MM-DD`, or `''` when empty) through the existing `modelValue` / `update:modelValue`. What the user sees follows the browser's locale; that is the browser's, not ours.
- Two optional props, `min?: string` and `max?: string`, bound to the input (not to the textarea). They are meaningful for `date` and `number` and are harmless elsewhere.
- Styling: the same tokens as every other type. Added only: `color-scheme` follows the theme so the native picker and its indicator are legible in dark mode, and the empty date field's placeholder segments use `--textbox-placeholder` where the engine exposes them (`::-webkit-datetime-edit` parts). No custom indicator icon.

## 4. Implementation strategy

One union member, two props, two bound attributes, and a short scoped style block for the date parts. `useBufferedModel` is unchanged: a date input emits `input` with a complete value or `''`, which the buffer already handles.

## 5. Hard stops

- **Public API surface:** additive (`'date'`, `min`, `max`). Recorded in `docs/public-api.md`.
- **Accessibility:** the native control brings its own keyboard and screen-reader support; label, description and error stay FormField's, tied by the existing `id`.

## 6. Tests

Unit (`TextboxBase.test.ts`, 36 tests today): renders `type="date"`; emits the ISO string; `min`/`max` reach the input; empty emits `''`; the buffered model keeps a typed value while focused; axe passes inside a FormField. Playground: a date textbox in its states (empty, set, disabled, error), both themes.

## 7. Backward compatibility

Every existing type renders and behaves as today.

## 8. Out of scope

A designed calendar (DatePicker); date ranges as one control; time and datetime types; formatting or parsing helpers.

# RFC 2.7.0-C — A dropdown and a textbox in one row stand at one height

## Affected components

`src/inputs/textboxes/Base.vue`, `src/inputs/dropdowns/components/Trigger.vue`, `src/styles/tokens.css`

## 1. Summary

A DropdownBase trigger and a single-line TextboxBase side by side differ by 1.5 px. Both adopt one height token and stand at the same height, without either's text size changing.

## 2. Current behavior (main 4b60031)

Both controls have the same vertical padding, `calc(0.625rem * var(--density-scale))`, and a 1 px border (`textboxes/Base.vue:155,160`; `dropdowns/components/Trigger.vue:60,65`). Their height differs only through the text size: `--textbox-size: var(--text-lg)` = 16 px (`tokens.css:410`) and `--dropdown-size: var(--text-md)` = 15 px (`tokens.css:444`). At the base line height that is 46 px against 44.5 px in one row.

## 3. Proposed behavior

A new semantic token:

```
--control-height: calc(2.875rem * var(--density-scale));   /* 46px at density 1 */
```

- `.textbox__input` (single-line only, never `--multiline`) and `.dropdown-trigger` get `min-height: var(--control-height)`, `box-sizing: border-box`; the trigger already centres its content (`align-items: center`).
- 46 px is the textbox's height today: **the textbox does not move; the dropdown trigger grows by 1.5 px.**
- Neither text size changes.

## 4. Alternatives considered

- *Unify the two size tokens* (dropdown to 16 px, or textbox to 15 px): changes text size in every dropdown or every textbox in the product, and leaves the heights equal only by coincidence of two unrelated tokens.
- *Fixed `height`*: breaks a trigger whose `selected` slot holds taller content; `min-height` does not.

## 5. Hard stops

- **Token architecture:** one new semantic token, density-scaled like the spacing tokens of 2.3.0; referenced by two components. No palette change.

## 6. Tests

Contract (Playwright, real layout): a DropdownBase and a TextboxBase in one flex row measure the same height at density 1 and at the compact density, in both themes; a multiline textbox keeps its own height. Playground: the two side by side.

## 7. Backward compatibility

Every DropdownBase trigger becomes 1.5 px taller (44.5 → 46). No API change. Forms in the dashboard are looked over for a moved control when the dependency is raised.

## 8. Out of scope

Buttons, the file input and other controls' heights: measured during implementation and **named in the release notes** if they differ from 46, not changed here.

# RFC 2.7.0-D — An unchecked radio's ring meets 3:1 (and the checkbox's with it)

## Affected components

`src/styles/palette.css`, `src/styles/tokens.css`, `src/styles/tokens-dark.css` (no component source changes)

## 1. Summary

The resting ring of an unchecked Radio is too faint to identify the control. Its border token is re-pointed to a new mid grey in each theme so the ring measures at least 3:1 against the page and a card (WCAG 2.2 SC 1.4.11, Non-text Contrast). The Checkbox's resting border moves with it.

## 2. Current behavior (main 4b60031), measured

The ring is `border: 2px solid var(--radio-border)` (`Radio.vue:87`).

| Theme | `--radio-border` | on the page | on a card |
| --- | --- | --- | --- |
| Light | `--color-neutral-500` #D1D1D1 (`tokens.css:155`) | 1.46:1 (#FAFAFA) | 1.40:1 (#F5F5F5) |
| Dark | `--color-nord-border` #454B5E (`tokens-dark.css:117`) | 1.54:1 (#2B2F3A) | 1.33:1 (#343947) |

The checkbox's resting border uses the same two colours (`tokens.css:144`, `tokens-dark.css:106`; `checkboxes/Input.vue:37`) and measures the same.

**Neither palette holds a grey that fits.** Light: neutral-900 #A0AEC0 is 2.16:1, the next step neutral-1000 #657B83 is 4.27:1. Dark: nord-elevated #5B6380 is 2.25:1; the next neutrals are text colours at 5:1 and above. Jumping to those would make every ring as heavy as body text.

## 3. Proposed behavior

Two palette colours are added (palette layer, no semantic meaning there):

| Token | Value | on the page | on a card | on white |
| --- | --- | --- | --- | --- |
| `--color-neutral-950` (light) | #8C8C8C | 3.22:1 | 3.08:1 | 3.36:1 |
| `--color-nord-control-border` (dark) | #7D869E | 3.68:1 | 3.17:1 | — |

Re-pointed, per theme: `--radio-border` and `--checkbox-border`. Checked, hover, error, disabled and focus tokens are untouched.

The exact values are **proposed**: they are the lightest greys of each palette's own hue that clear 3:1 on both grounds with a margin; a different shade at or above 3:1 on both grounds satisfies this RFC equally.

## 4. Why the checkbox moves with the radio

Color doctrine §11: checkbox, radio and switch are one family and must not diverge. The checkbox fails the same criterion by the same measure; fixing one and leaving its sibling would create the divergence the doctrine forbids. (Switch's off state is a filled track, a different shape, and is measured during implementation and named in the release notes.)

## 5. Measured and deliberately left

`--textbox-border` and `--file-upload-border` use the same light grey (`tokens.css:128,326`) and the dropdown trigger borrows the textbox's. A text field's border is also below 3:1 (on white: 1.53:1). It is **not** changed here: a field is additionally identified by its filled surface (`--textbox-bg`, which color doctrine §7 requires to differ from the page), darkening every field border changes the whole product's look, and that is a design decision of its own. It is named here so it is a known open item, not a silent one.

## 6. Hard stops

- **Accessibility guarantees:** raises non-text contrast to WCAG AA; CLAUDE.md §6 already claims AA.
- **Token architecture:** two palette entries added, four semantic tokens re-pointed (two per theme). Layers kept; no hex outside `palette.css`. Color doctrine §8 lists text contrast and focus-ring visibility but says nothing of a control's own boundary: this RFC proposes adding one line there — *"A control's resting boundary ≥ 3:1 against the surface it stands on."*

## 7. Tests

- A token test (`src/__tests__/styles/contrast.test.ts`, new): resolves `--radio-border` and `--checkbox-border` through palette.css in each theme and asserts ≥ 3:1 against `--general-body-bg` and `--general-card-bg`, so a later palette edit cannot regress it silently.
- Existing Radio (10) and Checkbox tests unchanged and green. Playground: radio and checkbox unchecked on the page and on a card, both themes.

## 8. Backward compatibility

Visual only: every unchecked radio and checkbox gets a darker ring. No API change.

## 9. Out of scope

Field borders (5); the disabled ring (exempt from AA by color doctrine §8, kept readable).
