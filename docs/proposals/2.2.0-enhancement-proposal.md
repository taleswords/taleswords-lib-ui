**Title:** Density System, Generic Badge, and Form Display Mode
**Status:** Accepted

# 1. Executive Summary

Version 2.1.0 established foundational capabilities for data-heavy panels (multiline input, display primitives, accordion initialization).

Version 2.2.0 focuses on systemic UI maturity:

1. Introduce Density & Spacing Token Layer
2. Introduce Generic BadgeBase (status/severity capable)
3. Add Display Mode to FormField

This release is purely additive and non-breaking.

Version bump: **Minor (2.2.0)**
Rationale: introduction of new tokens + new component capability + expanded component API.

---

# 2. Strategic Motivation

As lib-ui adoption expands within dashboard and editor surfaces, we encounter:

* Dense inspector panels
* Metadata-heavy sidebars
* Governance / status indicators
* Admin dashboards with compact layouts

Current limitations:

2.2.0 addresses these at the architectural level.

# 3. Enhancement 1 — Density & Spacing Token Layer

## 3.1 Problem

Spacing inside components is currently hardcoded (em/px values per component). There is no global way to shift UI density.

Inspector panels and sidebars require tighter vertical rhythm.

---

## 3.2 Proposal

Introduce density tokens at the semantic layer:

```
--density-scale
--space-xs
--space-sm
--space-md
--space-lg
--space-xl
```

Component spacing refactor (non-breaking):

* Replace hardcoded padding/gap with spacing tokens
* Default density-scale = 1
* Allow root-level density override:

```
[data-density="compact"] {
  --density-scale: 0.85;
}
```

Spacing tokens computed via:

```
calc(base * var(--density-scale))
```

---

## 3.3 Scope Constraints

* No visual change at default density
* Compact mode must not break layout
* No per-component density prop (global only)
* No breaking CSS selectors

---

## 3.4 Doctrine Compliance

* Token-layer expansion encouraged by CLAUDE.md §4
* No hex values
* Semantic token architecture preserved
* Backward compatible

---

## 3.5 Risk Assessment

Risk: **Medium (surface area)**
Mitigation: refactor incrementally, verify visually, preserve defaults.

# 4. Enhancement 2 — Generic BadgeBase

## 4.1 Problem

Current BadgeBase variants are role-locked (visitor, admin, public, pending, etc.).

There is no flexible badge for:

* Severity levels
* Status states
* Arbitrary labels
* Governance signals

---

## 4.2 Proposal

Enhance BadgeBase OR introduce new StatusBadgeBase.

Preferred approach: extend BadgeBase with new variant system.

New props:

```
variant?: 'neutral' | 'info' | 'success' | 'warning' | 'danger'
size?: 'sm' | 'md'
```

Existing role variants remain intact for backward compatibility.

Internally map to semantic tokens:

```
--badge-bg
--badge-text
--badge-border
```

No palette-level hex values allowed.

---

## 4.3 Backward Compatibility

* Existing role variants unchanged
* New variant prop optional
* No renaming

---

## 4.4 Risk Assessment

Risk: **Medium** (variant API expansion)
Mitigation: additive only, no variant removals.

---

# 5. Enhancement 3 — FormField Display Mode

## 5.1 Problem

FormField currently assumes interactive control:

* Pointer cursor on label
* Focus-within highlight
* Input-oriented structure

This is inappropriate for readonly metadata.

---

## 5.2 Proposal

Add optional prop:

```
display?: boolean
```

When display === true:

* Remove pointer cursor
* Disable focus-within accent color
* Suppress validation affordances
* Render label with display styling

This allows FormField to wrap DisplayFieldBase or readonly content semantically.

---

## 5.3 Non-Goals

* Do not convert FormField into interactive/display hybrid logic monster
* Keep implementation minimal and stylistic only

---

## 5.4 Risk Assessment

Risk: **Low**
Additive styling toggle only.
